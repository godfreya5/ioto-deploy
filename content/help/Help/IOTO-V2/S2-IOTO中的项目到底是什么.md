# IOTO中的项目到底是什么

这些年，我在各种直播里其实反反复复都讲过「项目」这件事。讲多了，反而发现一个现象：很多人一听「项目」两个字，脑子里立刻浮现的是甘特图、里程碑、WBS、项目经理、交付物……然后就被吓退了。

其实真没必要把项目想得那么复杂。

说到底，**一个项目，本质上就是一个对未来的期待，加上对未来要做的事情的一个汇总。** 就这么简单。

下面，我就基于之前讲过的那些内容，把 IOTO 里的「项目」这事，彻底讲清楚。

## 从 Project 这个词说起

我们今天用的「项目」一词，和最早中文里的「项目」其实不是一回事。最早的中文「项目」，更接近我们现在说的「条目」「款项」。

是日本学者比我们更早接触英文，在翻译 Project 这个词时，从中文里借用了「项目」二字；后来这层日本翻译又反过来影响了我们的用法，才有了今天对「项目」的理解。

所以，与其在中文里绕，不如直接看英文的 Project 本身：

- 前缀 **Pro**，表示「向前」，比如 progress（前进）；
- 词根 **ject**，表示「投掷、投射」，比如 eject（喷射）。

所以 Project，就是**向前投射**。我们平时说的投影仪，英文叫 Projector，就很形象——把光投到前方去。

理解了「向前投射」，项目这个词就非常好懂了：**项目，一定是对未来的投射。**

## 所以，IOTO 里的项目到底是什么

把上面的线索串起来，一个项目，往往就是我们：

> 对经过一段时间后，想要在某个领域、或者某件事情上，达到的新的高度或进展，所形成的一个整体的计划与期待。

再翻成大白话，就是开头那句——**它是你对未来的一个期待，也是你为未来要做的事情做的一个汇总。**

这里有两个绕不开的特征，也是我判断「这是不是一个项目」的尺子：

1. **项目一定是面向未来的。** 它指向还没发生的事。已经做完的、正在发生但无预期的，都不算。
2. **项目一定是有时间上的限制的。** 哪怕这个限制不是「截止日期」，也至少是一段你心里默认的跨度。

就这么两条，够了。不要再去套什么复杂的项目管理范式。

## 和 PARA 里的「项目」有什么不同

必须承认，IOTO 在诞生过程中，确实受到了 PARA 方法的影响。

但就我个人而言，PARA 里把 Project（项目）和 Area（领域）分得那么清，在做知识管理的时候，有点多此一举。退一步说，**没有必要把 Area 和 Project 区分得那么明确，能省则省，留一个「项目」足矣。**

这是 IOTO 和 PARA 在「项目」概念上最大的不同：

- **PARA 的 Project** 强调「有明确截止日期、有明确最终目标」的短期工作，与之相对的是长期维持的 Area。二者井水不犯河水。
- **IOTO 的项目** 则不拘泥于「有没有截止日期」。它既是你对未来的期待，也是未来要做事情的汇总——可以是一个有死线的交付，也可以是一个你打算长期推进、暂时没有终点的方向。

换句话说，IOTO 把「项目」这个概念放宽了、也减轻了。它不再是一个需要严阵以待的管理对象，而只是你脑子里「将来要去的地方」的一个落点。

## 项目可大可小，可长可短

项目如何划分，并没有必须恪守的依据。如果粗浅地分，我个人习惯分成两类：

- **有明确截止日期的。** 比如给某个机构做的培训服务，到点就得交付。
- **没有明确截止日期的。** 比如 IOTO 的研发，对我而言就是一个项目，但它没有终点，会一直往前走。

至于在你的知识管理实践里怎么划，完全看你自己实际情况来定。别被标准绑架。

## 知识管理的项目，不等于业务项目

还有一层要分清：**知识管理里的项目，和一个实实在在的业务项目，是不一样的。**

业务项目讲究交付、资源、排期，那是另一套严肃的工程。而你在 IOTO 里管理的项目，更多是「我想往哪个方向长」的一种整理方式。

所以我也一直说：**你可以在 IOTO 框架的基础上去管理你的项目，但如果想在 Obsidian 里把所有的项目管理需求都实现，其实是没有必要的。** 别把笔记软件硬拗成一个完整的 PM 工具。

## 无项目，不管理

最后回到一句老话：**无项目，不管理。**

不管你是用 IOTO 的 `3-任务` 文件夹去承载项目，还是只是用一张简单的任务清单去汇总未来的事，只要你脑子里有「项目」这个概念，你就在管理你的未来。

项目不需要复杂。它只是你对未来的一次投射。
