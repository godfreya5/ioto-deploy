# IOTO 中的项目，为什么是先建在任务文件夹下的

刚用 IOTO 的人，常常会卡在一个动作上：

> 创建项目，不是在「项目」文件夹下建项目，而是在 `3-任务` 文件夹下建一个项目的子文件夹。

这太违反直觉了。很多人会问：为什么不是建一个叫「项目」的一级文件夹，然后在下面放一个个项目？这一节，我们就把这件事讲清楚。

---

## 一、一个看似合理的直觉

假设你建了一个一级文件夹「项目」，下面再放一个个项目子文件夹。

接着问自己：在每个项目文件夹里，你准备放什么？

- 项目规范？
- 项目资料？
- 项目的产出？
- 关于项目的反思？
- 还是完成项目过程中，你做的一件件具体的事？

或者，你想把上面这些**全都**塞进同一个项目文件夹里。

不是不可以这么做——甚至我相信，很多人就是这么做的。一个项目一个文件夹，非常合乎现实经验里的逻辑。

**但问题是，这样非常不好管理。** 不仅是不好让人管理，也非常不适合电脑、程序、AI 去管理。

---

## 二、IOTO 的解法：把「文件夹」看成「数据表」

IOTO 的核心不是「文件归类经验」，而是一种**数据思维**。

IOTO 里那几个文件夹，本质上对应的是数据库里的几张数据表：

| 文件夹 | 角色 | 对应的「数据表」 |
|--------|------|------------------|
| `1-输入` | 外部获取的资料、素材、摘录 | 输入表 |
| `2-输出` | 个人思考、推演、理解沉淀 | 输出表 |
| `4-成果` | 可交付、可发布的成品 | 成果表 |
| `3-任务` | 具体要做的一件件事 | **任务表（C 位）** |

一个项目里，确实要处理各种类型的数据：资料（输入）、给别人的要求与指导、形成的报告（成果）、自己的反思备忘（输出），以及统筹一切的**一件件具体事项（任务）**。

在这四类数据里，**任务才是被操作得最高频的那个**。我们是通过「一个个任务的完成」，去一步步把项目走完的。

所以在这套数据模型里，**任务表站在 C 位**——而在你的 OB 库里，它就是 `3-任务` 文件夹。

---

## 三、项目为什么建在「任务」文件夹下

逻辑就顺了：

- `3-任务` 文件夹存放的是你创建的一个个**任务**，而任务是要和**项目**关联的；
- 所以，我们在 `3-任务` 下创建**项目的子文件夹**。当你往里面建任务时，系统会自动给每个任务带上对应的**项目属性**；
- 这样，**项目和任务就关联起来了**；
- 之后，当我们在某个任务笔记里去创建输入、输出、成果时，可以直接把该任务笔记里的「项目属性」继承过去——输入、输出、成果也就顺着任务，和项目关联了起来。

整条关联链就是：

```
项目（3-任务下的子文件夹）
  └─ 任务（自动带上项目属性）
       ├─ 输入（继承项目属性）
       ├─ 输出（继承项目属性）
       └─ 成果（继承项目属性）
```

走通这一条，项目就不再是「一个装所有东西的大抽屉」，而成了贯穿输入 / 输出 / 任务 / 成果四张表的一条**主线**。

---

## 四、核心工作流：以项目为中心，以任务为驱动

回顾一下这两组动作的频次：

- **创建项目**：低频操作，建一次管很久；
- **创建任务**：高频动作，几乎每天都在发生。

IOTO 的设计思路，就是顺着这个真实频次来摆放结构——把低频的「项目」挂到高频的「任务」之下，再用任务作为统一场景，去完成一个个相关的输入、输出或产出。

周而复始，循环往复，直到项目结束。

这就是我一直说的：

> **以项目为中心，以任务为驱动。**

当你理解了「项目建在任务文件夹下」不是别扭的约定，而是为了让人和机器都能顺着同一条主线去管理数据，这个反直觉的设定，也就成了 IOTO 最基本、最核心的工作流入口。
